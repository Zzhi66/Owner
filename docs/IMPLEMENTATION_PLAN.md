日期：2026-10-16

状态：P0 已完成，P1 界面与交互迁移已实现且主要流程已验证；进度见 [实施清单](ROADMAP.md) 与 [P1 记录](P1_REACT_MIGRATION.md)

## 1. 交付目标与范围

将当前贾维斯风格原型逐步做成可长期记录和查看个人信息的应用。第一版采用浏览器运行、本地优先的方式，完成真实日期、可靠存储、备份恢复与各领域记录闭环；后续按需求加入同步、真实 Agent、局部 Three.js 视觉和桌面封装。

必须保持的产品结构：

- 总览顺序为资产 → 今日待办（含日程）→ 个人近况。
- 近况包含身体、饮食、学习 / 工作、习惯，用户可调整卡片顺序。
- 心情与精力归入身体，阶段目标归入学习 / 工作。
- 总览呈现摘要，历史数据和完整记录放在领域详情。
- Agent 保持右侧点击展开的悬浮窗，包含对话、任务、产物。
- 保留中文界面、HUD 视觉、金额隐藏、键盘操作和手机布局。

第一版交付以阶段 P0–P4 全部验收为准。联网同步、真实模型、3D 与桌面安装均为后续可选阶段，不作为第一版完成条件。

## 2. 技术选型

| 层级 | 计划采用 | 使用范围与约束 |
| --- | --- | --- |
| UI | React + TypeScript | 按领域拆分组件，启用严格类型检查；沿用现有页面结构 |
| 工具链 | Vite + npm | 开发热更新、构建、锁文件；继续使用当前 npm 工作流 |
| 样式 | CSS Modules + 全局 CSS 变量 | 将 HUD 配色、间距、字体抽为变量，组件样式逐步迁移 |
| UI 状态 | React state / reducer / context | 管理弹窗、Agent 开合、筛选；首版不额外引入全局状态库 |
| 本地存储 | IndexedDB + Dexie | 领域记录与偏好分表，事务写入、版本迁移 |
| 数据校验 | Zod | 表单、迁移输入、导入文件、未来同步与 Agent 工具参数 |
| 图表 | Apache ECharts | 趋势、构成、热力图，按使用的图表类型加载 |
| 单元 / 集成测试 | Vitest | 日期、统计、迁移、备份及关键业务边界；数据库测试可配合 fake-indexeddb |
| 组件测试 | React Testing Library，按需加入 | 表单错误、取消不写入、键盘交互等用户可观察行为 |
| 代码质量 | TypeScript、ESLint、Prettier | 类型、静态规则和格式分别检查，避免只靠语法检查 |
| 后续 3D | Three.js + React Three Fiber | 仅局部视觉增强，加载失败可降级为 SVG |
| 后续桌面 | Tauri + SQLite | 确定安装形态后再实施，保留领域服务与大部分 UI |

React 官方提供 Vite + TypeScript 的应用搭建路径；本项目据此选择客户端应用方案。[React 文档](https://react.dev/learn/build-a-react-app-from-scratch)、[Vite 文档](https://vite.dev/guide/)

Dexie 封装 IndexedDB 并提供数据库版本升级机制；Zod 用于运行时校验，ECharts 用于统计图表，Vitest 用于测试。[Dexie 文档](https://dexie.org/docs/)、[升级机制](https://dexie.org/docs/Version/Version.upgrade())、[Zod](https://zod.dev/)、[ECharts](https://echarts.apache.org/en/index.html)、[Vitest](https://vitest.dev/guide/)

版本策略：实施 P0 时选用彼此兼容的稳定版本，核对 Node 要求后写入锁文件，不在本文预先固定所有依赖补丁版本。当前验证过的 Node 为 22.22.0；后续如需升级，更新 `.nvmrc` 和开发指南。3D 接入时必须核对 React 与 R3F 的主版本兼容关系，避免混用不匹配的渲染器。[R3F 官方说明](https://r3f.docs.pmnd.rs/getting-started/introduction)

## 3. 架构与目录

采用单仓库、单前端应用，先明确模块边界，不拆微服务或多包工作区。

```text
React 页面 / 表单 / Agent 工作窗
                ↓
领域服务：校验、日期、统计、任务转换、导入恢复
                ↓
存储接口：查询、写入、事务、迁移
                ↓
Dexie / IndexedDB

后续可增加 SQLite 存储适配与 Agent 服务适配
Three.js 只消费界面状态，不直接读写业务数据库
```

目标目录如下，按阶段建立；P1 已建立 app、components、features、domain、data 及共享样式，数据库与正式服务目录在 P2 创建：

```text
index.html
src/
  app/                     # 应用入口、hash 路由、全局 providers
  components/              # Panel、Dialog、Field 等共享控件
  features/
    overview/              # 组合各领域摘要
    body/ diet/ habits/    # 领域页面、表单、组件
    work/ assets/ tasks/
    calendar/ goals/ agent/ settings/
  domain/
    models/                # TypeScript 类型与 Zod schema
    services/              # 统计、任务转换、导入等业务逻辑
    ports/                 # 存储与 Agent 接口
  data/
    indexeddb/             # Dexie 表、索引、查询与事务
    migrations/            # 原型数据迁移、数据库升级
    fixtures/              # 明确标注的示例数据
  shared/
    date/                  # 可注入时钟、日期范围、本地日期规则
    styles/                # reset、tokens、基础 HUD 样式
  visuals/
    CoreVisual.tsx         # 默认 SVG，未来可替换为局部 3D
tests/                     # 跨模块业务测试与固定测试数据
dist/                      # 现有手写原型，继续保留并跟踪
build/                     # 新应用构建产物，忽略提交
docs/
reference/
```

P2 起，数据库作为领域记录的唯一持久来源；React 中只保存编辑草稿和展示状态，避免同时维护两套互相覆盖的数据。P1 过渡期仍通过 `src/data/prototype.ts` 和 `src/app/usePrototype.ts` 兼容 localStorage v1，类型与纯选择器分别位于 `src/domain/models.ts`、`selectors.ts`。Dexie 的订阅与 hooks 后续封装在数据适配层，领域计算保持纯函数。存储接口按实际用例定义，例如按日期查记录、保存任务、原子导入，不为所有实体堆叠通用抽象。

首版保留现有 `#overview`、`#body` 等 hash 入口，实现导航、前进后退与未知路径回退；页面数量和嵌套路由增加后再评估独立路由库。

## 4. 数据设计与保留策略

### 4.1 主要实体

| 数据 | 计划模型及关键约束 |
| --- | --- |
| 身体、心情 | DailyBodyRecord、WellbeingRecord；同一工作空间同一天各一条，缺失值与零值区分 |
| 饮食、专注 | MealRecord、FocusSession；每天可多条，原始值与估算值区别展示 |
| 习惯 | HabitDefinition、HabitLog；按习惯 ID + 日期唯一，支持配置与停用 |
| 待办 | Task；关联目标可选，包含日期与完成时间，重复点击不会重复创建目标行动 |
| 日程 | CalendarEvent；区分全天日期与带时间的事件，首版为单次日程 |
| 目标 | Goal；进度 0–100，保持当前最多 3 个目标的规则 |
| 资产 | Account、AccountSnapshot；金额采用整数分，首版人民币，不隐含自动汇率换算 |
| 其他 | Note、AgentTask、Artifact、ConversationMessage、Preference |

实体包含稳定 ID、工作空间标识、来源和适用的业务日期。新增记录包含真实创建 / 更新时间；旧数据未知的创建时间保留为空，另记迁移时间，不能把迁移时间冒充历史创建时间。已有资产历史若与账户快照无法对应，按“原型历史估值”单独保留，不能伪造为可核对的账户流水。

### 4.2 原型、示例与正式记录

旧 key `owner.workbench.prototype.v1` 内可能混有示例和用户手动记录，且部分实体没有来源字段。不能简单地将整库标成正式数据，也不能按标题推断并删除所谓示例。

迁移采用以下流程：

1. 读取旧值，不修改、不删除；提供原始 JSON 下载备份。
2. 校验结构并展示记录数量、日期范围、来源不明情况；解析失败时保留原内容并提供恢复入口。
3. 将旧数据整体导入隔离的“原型记录”空间，保留原日期与来源信息；不明来源标记为未知。
4. 在事务内写入记录和迁移标记，失败不留下半成品；重复启动不会重复导入。
5. 新建“正式记录”空间，默认空数据，使用真实日期；“示例体验”使用独立数据空间和固定示例日期。
6. 用户需要旧记录进入正式空间时，先按领域 / 日期预览再复制。来源不明项由用户决定，不自动移动。

界面明确显示当前空间。复制记录时保留原始日期和关联映射；不得为了适配今天而平移历史日期。迁移后的新记录不会反向同步到旧原型，回到旧界面前应先导出新版备份。

### 4.3 日期与统计

- 引入可注入的 Clock / DateService，测试不依赖执行当天。
- 日记录使用 `YYYY-MM-DD` 本地日历日期，创建和更新时间使用 UTC 时间戳。
- 首版以设备本地时区为默认；日历日期不使用 UTC 截断生成。
- 近 7 / 30 天按本地日历日计算，包含今天；睡眠记录明确采用起床日期。
- 页面跨过午夜、后台恢复或重新获得焦点时重新计算当天，不能一直使用启动日期。
- 全天日程保存日期；有具体时间的日程保存本地日期、时间和时区语义，展示不混用 UTC 与本地时间。
- 明确定义缺失记录、未来日期、未完成过期待办、缺少完成时间的旧任务如何统计，并覆盖测试。

### 4.4 备份、恢复与删除

- 备份包含格式版本、应用版本、导出时间、工作空间、记录及必要偏好；凭据不进入普通备份。
- 导入先检查大小、JSON、schema 版本、字段类型、ID 与关联关系，再展示变化预览。
- 首版优先支持导入为独立恢复空间，以及经确认替换指定空间；同库合并和冲突自动处理后置。
- 替换前创建恢复点，写入与切换使用事务；失败保持原空间可用。
- 常规删除提供回收站或撤销窗口，目标删除后已生成的待办保留，解除关联。
- 申请浏览器持久存储可以作为增强，但不能替代文件备份；浏览器空间被清理仍可能丢失本地数据。

IndexedDB 与浏览器及站点来源绑定，域名、协议和端口变化会影响可访问的数据。开发切换尽量保持 `http://127.0.0.1:4173`；不同地址只能通过用户导出的文件迁移。[Dexie React 使用说明](https://dexie.org/docs/Tutorial/React)

## 5. 分阶段执行与验收

顺序：P0 → P1 → P2 → P3 → P4。每一阶段完成后留下可运行版本，先验收再切换下一阶段。

### P0 · 建立工程骨架

工作：创建 React + TypeScript + Vite 入口、严格类型检查、lint、格式化与 Vitest 配置；建立上述核心目录，配置 `build.outDir = 'build'`。保留现有 `dist/` 和 `server.cjs` 作为原型参考。

在准备好切换前，现有 `npm run dev` 仍运行原型，新应用使用单独脚本和备用端口。该阶段只用测试数据，不从备用来源假定能读到原型 localStorage。统一入口切换时，再将新应用接管 4173，保留原型启动脚本。

交付：工程骨架、锁文件、命令说明、可打开的新入口。

验收：干净环境下依赖安装成功，类型与静态检查通过；构建只写 `build/`，构建前后 `dist/` 内容不变；原型仍能独立运行。此阶段不进行业务数据迁移。

### P1 · React 界面与交互迁移

工作：将导航、顶部控制台、资产摘要、待办、近况卡片、领域页、表单和 Agent 工作窗逐块迁为组件。抽出全局 HUD tokens，随后迁移各组件 CSS Modules，避免一次性重写全部样式。

组件只通过过渡存储适配访问现有数据。过渡版本继续使用原型日期和明确的原型标识；不在视觉迁移中混入真实日期切换。表单草稿仅在提交成功后写入。`CoreVisual` 暂时仍渲染 SVG。

交付：与当前预览功能等价的 React 版本、组件结构和视觉对照截图。

验收：现有全部交互保留，导航 / 刷新 / 前进后退正常；资产隐藏、卡片顺序和已保存记录不丢失；375、768、1024、1440 像素布局可用；Agent 浮窗、Esc、弹窗焦点和返回焦点正常。

当前实现已覆盖上述组件和过渡存储，`npm run verify` 全部通过（57 项测试、类型、lint、格式、语法和构建），构建前后 dist/ 指纹保护通过。导航、待办、心情、日程和目标等主要流程已完成浏览器验证；尚未检查的广泛手动项单独保留，不等同于全部验收完成。React 统一开发入口切换为 4173，原型对照改为 4174，生产预览为 5175。只有同一来源的旧 localStorage 可直接读取，不对 P0 的 5173 或其他地址自动合并。无效旧结构保留原始内容并暂停写入；正式日期、Dexie 和隔离空间仍由 P2 负责。详见 [P1 迁移记录](P1_REACT_MIGRATION.md)。

### P2 · 正式日期与可靠存储

工作：定义 Zod schema、Dexie 表和索引、领域存储接口、日期服务；实施第 4 节的旧数据迁移与空间隔离。UI 完成从过渡适配到 Dexie 的切换。

交付：真实日期模式、独立示例体验、原型记录空间、迁移报告和错误恢复入口。

验收：重复迁移无重复数据；迁移中断可重试；无效旧数据不被覆盖；刷新保留数据；两个标签页能感知记录变化，编辑冲突至少明确提示而非静默覆盖；跨天、跨月、跨年及夏令时边界测试通过。

### P3 · 记录闭环与备份恢复

工作：补齐各领域增删改查、习惯配置、单次日程、目标行动关联，以及数据导入、导出、恢复点和删除恢复。资产建立账户快照，快照变化可追溯，金额显示与存储单位一致。

交付：可日常使用的数据记录与恢复流程。

验收：取消编辑不写入；保存失败保留草稿；空值、范围、重复记录和关联错误有明确反馈；目标重复加入待办被阻止；备份往返后实体和关联一致；坏文件、未知新版备份、超限文件均不改变原数据；演示 / 原型数据不会进入正式统计。

### P4 · 统计图表与第一版验收

工作：接入按需加载的 ECharts，统一睡眠趋势、习惯热力图、投入统计及资产构成；保留小型 SVG 指标和装饰。图表旁提供单位、时间范围、来源与必要的文本摘要。补齐生产构建检查与关键流程验收。

交付：本地优先的第一版应用、数据说明、恢复指南、已知限制和发布检查记录。

验收：图表与记录列表统计一致；缺失值不伪造为零；没有数据时展示空状态；图表卸载释放资源；网络断开时已加载应用仍可完成本地记录；不将此验收等同于已实现可离线冷启动的 PWA。

本阶段要求 `typecheck`、`lint`、业务测试、生产构建通过，核心流程完成浏览器验收。当前仓库的 `npm run check` 仅检查语法，P0 后需建立新的检查脚本并明确命令含义。

### P5 · 数据接入与真实 Agent（后续）

前提：P4 完成，并确定首个实际数据来源和模型运行方式。

数据接入先做一个真实来源，定义授权、来源 ID、同步游标、去重、冲突和重试。导入完成前展示预览，保留手动修改记录。不得为了展示同步状态生成假结果。

Agent 首先提供只读查询、近况总结和产物生成。定义 `AgentService`，输入为用户任务及明确选定的数据范围，输出为可取消的流式事件、任务状态与产物。记录所用来源和时间范围；模型不可直接访问数据库或任意执行代码。

浏览器方案需受控服务端处理模型凭据和外部调用；桌面方案可通过原生层实现。届时选择具体服务框架，不在当前前端计划中默认安装。写入动作后续通过受校验的领域命令实现，先预览、确认，再执行，并提供操作日志及适用的撤销。

验收：模型失败、超时、取消不产生虚假成功；工具参数经过 schema 校验；敏感数据只在明确选择的范围内发送；本地演示适配与真实适配在界面上明确区分。

### P6 · Three.js 局部增强（可独立安排）

前提：P4 稳定，且确认希望增加 3D 效果；不依赖真实 Agent 接入完成。

首个场景只改顶部核心：`CoreVisual` 提供 `svg` / `3d` 模式，采用 Three.js + React Three Fiber。后续才考虑 Agent 能量球或身体模型，不将表单、金额、常规统计迁入 Canvas。

视觉组件消费 `idle / thinking / responding / error` 等显式状态；演示任务与真实任务的文本标识继续保留。帧动画在渲染循环中更新，避免每帧触发全局 React 状态更新。

验收：3D 单独分包并按需加载；关闭 3D 时不加载相关模块；不可见 / 后台时停止不必要的渲染；遵守减少动态效果偏好；WebGL 不可用或上下文丢失时降级 SVG；卸载释放几何、材质和纹理。桌面以 60 fps、低性能模式以 30 fps 为初始目标，在实际测试设备上测量并记录，未达到则降低画质或保持 SVG。

R3F 是 React 的 Three.js 渲染器，允许场景参与 React 组件体系；它仍需要 Three.js 的场景和资源管理知识。[R3F 文档](https://r3f.docs.pmnd.rs/getting-started/introduction)

### P7 · 桌面交付（可选分支）

前提：明确需要安装包、本地文件数据库、系统通知或其他原生能力。

采用 Tauri 保留前端，增加 SQLite 存储适配及迁移工具。IndexedDB 到 SQLite 不是自动转换：需要字段映射、事务导入、关联验证、数量核对和回退方案。浏览器来源的数据通过版本化备份导出，再由桌面导入；不能假定 WebView 能直接访问原浏览器数据库。

验收：原型和正式记录可分别迁移；应用重启数据保留；升级失败不会损坏数据库；权限按功能授予；密钥通过适当的原生安全存储处理。SQLite 本身不意味着数据已加密；若需要加密备份或数据库，另立需求设计。

Tauri 的架构包含 WebView 与原生部分，官方 SQL 插件提供 SQLite 支持。[Tauri 架构](https://v2.tauri.app/concept/architecture/)、[SQL 插件](https://v2.tauri.app/plugin/sql/)

## 6. 验证矩阵

| 范围 | 必须覆盖的场景 | 手段 |
| --- | --- | --- |
| 日期 | 月末、年末、闰日、午夜刷新、跨时区 / 夏令时 | 可注入时钟的单元测试 |
| 统计 | 缺失值、零值、边界日期、未来记录、估值单位 | 纯函数测试与固定样本 |
| 迁移 | 混合来源、缺字段、重复导入、中断、损坏存储 | 存储集成测试与真实浏览器验证 |
| 备份 | 导出后导入、坏文件、新版本、替换失败 | 事务集成测试与交互验收 |
| 核心记录 | 添加 / 编辑 / 取消 / 删除恢复、刷新持久化 | 组件测试与浏览器验收 |
| 界面 | 375–1440 像素、键盘、焦点、弹窗、Agent 开合 | 实际浏览器检查与截图对照 |
| 性能 | 图表 / 3D 懒加载、长列表、资源释放 | 生产构建分析与性能面板 |

数据库模拟环境不替代真实浏览器对 IndexedDB 升级、事务和多标签行为的验证。测试数据独立，不通过清空用户 localStorage 获得干净环境。远程仓库确定后，再配置 CI 运行同样的检查。

## 7. 第一批可执行任务

以下任务对应 P0 和 P1 的首个小步，每项保持独立、可评审的变更：

1. 新建开发分支，确认原型运行和基线提交，保存当前视觉对照。
2. 配置 React / TypeScript / Vite，构建输出固定为 `build/`，保留原型启动入口。
3. 建立类型检查、lint、Vitest 脚本，验证 Node 与锁文件兼容。
4. 抽取 HUD tokens，迁移 AppShell、导航、顶部核心和空白内容容器。
5. 定义领域接口与测试样本，以资产卡片作为第一个完整迁移单元。
6. 对比原型布局、金额隐藏和导航行为，通过后再扩展到其他模块。
